# Аудит выгрузки

Две таблицы с одними и теми же обращениями: `tickets` (выгрузка как есть) и `clean` (она же после чистки, которую сделал коллега). Здесь я проверяю, что было не так в сырых данных, что он исправил и что пропустил.

Запуск из корня репозитория: `python3 src/run_sql.py analysis/01_data_audit.md`

## Сырые данные и чистка

### 1. Дубли и размер выгрузки

**Итог:** в `tickets` 7033 строки, разных номеров 6760, в `clean` 6760 строк: 273 строки (7033 − 6760) были дублями.

Дубли полные: если убрать повторы целыми строками (`SELECT DISTINCT *`), остаются те же 6760, то есть одно обращение попало в выгрузку несколько раз с одинаковыми полями. Коллега оставил по одной копии.

```sql
SELECT COUNT(*) FROM tickets;                      -- все строки выгрузки
SELECT COUNT(DISTINCT id) FROM tickets;            -- разные номера обращений
SELECT COUNT(*) FROM clean;                        -- строк после чистки
SELECT COUNT(*) FROM (SELECT DISTINCT * FROM tickets);  -- полные дубли убраны: тоже 6760
```

### 2. Каналы

**Итог:** в `tickets` пять значений канала: `чат` (2711) и `Чат` (163) записаны по-разному, плюс почта, телефон, форма; в `clean` четыре: `Чат` приведён к `чат`.

Другие поправки (удаление дублей) видны по уменьшению чисел: например, `чат` в `clean` 2770, а в `tickets` 2711 + 163 = 2874.

```sql
SELECT channel, COUNT(*) FROM tickets GROUP BY channel ORDER BY 1;
SELECT channel, COUNT(*) FROM clean GROUP BY channel ORDER BY 1;
```

### 3. Пустые темы

**Итог:** пустая тема в сырых данных записана двумя способами: пустой строкой `''` (287 строк) и текстом `NULL` (157 строк); коллега заменил `''` на `без темы` (278 после удаления дублей), а текст `NULL` оставил как есть (152 строки), то есть исправил не всё.

SQL-`NULL` в теме нет ни в одной из таблиц (`topic IS NULL` даёт 0): `NULL` в этом поле — просто слово из четырёх букв. Поэтому в `clean` «нет темы» записано двумя разными значениями (`без темы` и `NULL`), и при группировке по теме они считаются разными темами.

```sql
SELECT topic, COUNT(*) FROM tickets GROUP BY topic ORDER BY 1;
SELECT topic, COUNT(*) FROM clean GROUP BY topic ORDER BY 1;
SELECT COUNT(*) FROM tickets WHERE topic IS NULL;   -- настоящих NULL нет
SELECT COUNT(*) FROM clean WHERE topic IS NULL;     -- и в clean тоже
```

### 4. Форматы дат и период выгрузки

**Итог:** в формате `ДД.ММ.ГГГГ` 2119 строк, в другом (`ГГГГ-ММ-ДД`) 4914; «после 1 апреля» по `tickets` как есть 3337, по `period` в `clean` 3549; выгрузка охватывает период с 1 января 2025 по 30 июня 2025.

Числа разные по двум причинам. Во-первых, даты сравниваются как текст, а в формате `ДД.ММ.ГГГГ` первым стоит день: `'25.01.2025'` текстом больше `'2025-04-01'` (январь попал бы в «после»), а `'15.05.2025'` меньше (май не попал бы в «после»). Ошибка идёт в обе стороны. Во-вторых, в `tickets` ещё есть дубли. Поэтому для периода нужна дата в одном формате, как в `clean`.

```sql
SELECT COUNT(*) FROM tickets WHERE created_at LIKE '__.__.____%';      -- формат ДД.ММ.ГГГГ
SELECT COUNT(*) FROM tickets WHERE created_at NOT LIKE '__.__.____%';  -- другой формат
SELECT COUNT(*) FROM tickets WHERE created_at >= '2025-04-01';         -- сравнение текста как есть
SELECT COUNT(*) FROM clean WHERE period = 'после';                     -- по period в clean
SELECT '25.01.2025 10:00' >= '2025-04-01', '15.05.2025 10:00' >= '2025-04-01';  -- 1 и 0: январь после, май до
SELECT MIN(created), MAX(created) FROM clean;                          -- период выгрузки
```

## Пустые значения

### 5. Обращения без сотрудника

**Итог:** бот закрыл 1667 обращений, у 1570 из них нет сотрудника; у остальных 97 сотрудник есть, и все 97 клиент переоткрыл.

Пустой сотрудник значит, что человек не участвовал: бот ответил и закрыл обращение сам, все 1570 имеют статус `решено`. У остальных 97 обращение закрыл бот, но клиент его переоткрыл, и дальше его взял сотрудник. Значит, «закрыл бот» не равно «решено».

```sql
SELECT bot_result, COUNT(*), SUM(agent_id IS NULL) FROM clean GROUP BY bot_result;  -- закрыл: 1667 и 1570 без сотрудника
SELECT status, COUNT(*) FROM clean WHERE agent_id IS NULL GROUP BY status;          -- у обращений без сотрудника
SELECT status, reopened, COUNT(*) FROM clean
WHERE bot_result = 'закрыл' AND agent_id IS NOT NULL
GROUP BY status, reopened;                                                          -- остальные 97
```

## Нумерация

### 6. Пропущенные номера обращений

**Итог:** пропущено 187 номеров: 32 до 1 апреля и 155 после.

До апреля номера 1–3243, и пропущено около 1,0% (32 из 3243); после апреля номера 3244–6947, и пропущено около 4,2% (155 из 3704), то есть доля потерь выросла в четыре раза. Значит, часть обращений в выгрузку не попала, и после апреля потеряно больше. Если потерянные обращения не случайны (например, это как раз закрытые ботом или особо сложные), то доли и средние после апреля могут быть смещены.

```sql
SELECT MAX(num) - COUNT(*) FROM clean;     -- всего пропусков (номера начинаются с 1)
SELECT period, MIN(num), MAX(num), COUNT(*), MAX(num) - MIN(num) + 1 - COUNT(*)
FROM clean GROUP BY period;                -- пропуски по периодам
```

## Бот

### 7. Где работает бот

**Итог:** бот работает в письменных каналах: чат, почта, форма; в телефоне не участвует (все 861 телефонных обращений с `нет`); из 2688 письменных бот закрыл 1667 (62,0%) и передал человеку 1021 (38,0%).

По каналам: чат закрыл 922 и передал 502, почта 478 и 353, форма 267 и 166.

```sql
SELECT channel, bot_result, COUNT(*) FROM clean
WHERE period = 'после' GROUP BY channel, bot_result ORDER BY 1, 2;
SELECT COUNT(*), SUM(bot_result = 'закрыл'), SUM(bot_result = 'передал'), ROUND(AVG(bot_result = 'закрыл') * 100, 1)
FROM clean WHERE period = 'после' AND written = 1;   -- письменных 2688, закрыл 1667, передал 1021, доля закрытых 62,0%
```

### 8. Время первого ответа

**Итог:** в письменных каналах первый ответ ускорился с 64,0 мин (медиана 50,1) до 0,4 мин (медиана 0,4), а по телефону остался прежним: 3,7 мин (медиана 3,1) до и 3,6 мин (медиана 3,0) после; первым после апреля письменным обращениям отвечает бот.

Общее среднее по всем обращениям упало с 50,2 до 1,2 мин, но это складывается из письменных каналов, где теперь отвечает бот. Скорость работы людей по телефону не изменилась, поэтому по общему числу о людях судить нельзя. Опираться лучше на медиану и на разрез по каналам: среднее тянут вверх редкие очень долгие ответы.

```sql
SELECT period, written, ROUND(AVG(first_reply_min), 1), MEDIAN(first_reply_min), COUNT(*)
FROM clean GROUP BY period, written ORDER BY period DESC, written;   -- written = 0 это телефон
SELECT bot_result, ROUND(AVG(first_reply_min), 1), MEDIAN(first_reply_min), COUNT(*)
FROM clean WHERE period = 'после' AND written = 1
GROUP BY bot_result;     -- и закрытые, и переданные ботом получили ответ за 0,4 мин: отвечает бот
```

## Возвраты

### 9. Переоткрытия и возвраты

**Итог:** переоткрыто (`reopened`) 579 обращений и возвратов (`came_back`) 531; до апреля 273 и 200, после апреля 306 и 331 (6,2% до и 9,3% после для возвратов, а доля переоткрытых почти не изменилась: 8,5% и 8,6%).

Это разные события: переоткрытие это когда клиент вернулся в то же обращение, а возврат это когда тот же клиент создал новое обращение с той же темой в течение 7 дней. Для обращений без темы (`без темы` и `NULL`) возврат не считается и равен 0, поэтому он занижен.

```sql
SELECT SUM(reopened), SUM(came_back) FROM clean;
SELECT period, SUM(reopened), SUM(came_back), COUNT(*),
       ROUND(AVG(reopened) * 100, 1), ROUND(AVG(came_back) * 100, 1)
FROM clean GROUP BY period;
```

## Справочник

### 10. Справочник сотрудников

**Итог:** 18 сотрудников вели от 97 до 457 обращений каждый, без сотрудника 1570 обращений; сотрудник без обращений в справочнике один: `igor_h` (номер 19); в `clean` номер записан как `a01`–`a18` (буква и двузначное число), а в `agents` как `1`–`19` (просто число).

Из-за разного формата справочник нельзя напрямую соединить с обращениями: сначала номер надо привести к одному виду (убрать букву и превратить в число). Кроме того, в справочнике 20 строк, но 19 человек: `ivan_p` с номером 1 записан дважды.

```sql
SELECT agent_id, COUNT(*) FROM clean GROUP BY agent_id ORDER BY 1;   -- NULL это обращения без сотрудника
SELECT id, login, hired_at FROM agents
WHERE CAST(id AS INTEGER) NOT IN
      (SELECT CAST(substr(agent_id, 2) AS INTEGER) FROM clean WHERE agent_id IS NOT NULL);  -- сотрудник без обращений
SELECT DISTINCT agent_id FROM clean WHERE agent_id IS NOT NULL ORDER BY 1 LIMIT 3;   -- формат a01
SELECT id FROM agents ORDER BY CAST(id AS INTEGER) LIMIT 3;                          -- формат 1
```

## Чего нельзя утверждать по этой выгрузке сразу

1. **«С апреля первый ответ стал в 40 раз быстрее: было 50,2 минуты, стало 1,2.»** Нельзя: по телефону, где отвечают люди, время не изменилось (3,7 мин до апреля и 3,6 после). Ускорение только в письменных каналах, где первым отвечает бот (0,4 мин), и оно не говорит о работе людей.

```sql
SELECT period, ROUND(AVG(first_reply_min), 1) FROM clean GROUP BY period;           -- 50,2 и 1,2
SELECT period, written, ROUND(AVG(first_reply_min), 1) FROM clean GROUP BY period, written;  -- телефон 3,7 и 3,6
```

2. **«Бот закрыл 1667 обращений, значит, решил 1667 проблем.»** Нельзя: статус `закрыл` не проверяет, помог ли ответ. Из закрытых ботом клиент вернулся с тем же вопросом в 12,1% случаев (202 из 1667), а из переданных людям только в 6,9%; ещё 97 закрытых ботом обращений клиент переоткрыл.

```sql
SELECT bot_result, COUNT(*), SUM(came_back), ROUND(AVG(came_back) * 100, 1)
FROM clean WHERE period = 'после' AND written = 1 GROUP BY bot_result;   -- 12,1% и 6,9%
```

3. **«В конце июня возвратов стало меньше: доля упала до 6,0%, значит, качество выросло.»** Нельзя: возврат считается как повторное обращение в течение 7 дней, а выгрузка заканчивается 30 июня, поэтому у обращений последней недели возврат ещё не успел случиться. Для обращений с 23 июня доля 6,0% (19 из 316), хотя в апреле–июне в среднем около 9% по месяцам.

```sql
SELECT month, COUNT(*), ROUND(AVG(came_back) * 100, 1) FROM clean GROUP BY month;   -- по месяцам
SELECT COUNT(*), SUM(came_back), ROUND(AVG(came_back) * 100, 1)
FROM clean WHERE created >= '2025-06-23';   -- последняя неделя: 316, 19, 6,0
```
